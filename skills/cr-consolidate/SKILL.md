name: cr-consolidate
description: Consolidates the two /cr review files (cr_1 + cr_2), deduplicates findings, categorizes by severity and posts ONE comment on the PR. Final review step of the /cr pipeline; also usable standalone.
argument-hint: <PR-number>
user_invocable: true
---

PR_NUM="$ARGUMENTS"

Compute the file location (the repository is the one in the current working directory — never pass `-R`):

```bash
REPO_SLUG=$(gh repo view --json nameWithOwner -q .nameWithOwner | tr '/' '-')
OUT_DIR="/tmp/cr/$REPO_SLUG"
```

**Context:** `$OUT_DIR/cr_1_$PR_NUM.md` and `$OUT_DIR/cr_2_$PR_NUM.md` contain code review findings from two distinct agents. Each file starts with a standardized header (PR/SHA/Branch/Timestamp/Skill or Aspects run) followed by the literal skill output.

- `cr_1`: built-in `/code-review high` skill (parallel fan-out of review agents: guideline compliance, bug scan, git blame/history, previous PRs, code comments)
- `cr_2`: `/pr-review-toolkit:review-pr` plugin (specialized agents per aspect: errors, tests, types, comments, code, simplify)

**Your task:** read both files, deduplicate findings, categorize by severity and post ONE consolidated comment on the PR via `gh pr comment $PR_NUM --body-file -` (pass the body via heredoc/stdin to avoid problems with backticks in the body).

**Dedup:** two findings are the same if (a) they reference the same file, (b) the line is within ±3 lines, (c) they describe the same problem (same core verb + object, ignoring phrasing differences). When duplicated, keep ONE entry with `**Detected by:** cr_1 + cr_2` and use the **higher severity** of the two sources.

If the repository's PRs and comments are predominantly written in a language other than English, write the comment in that language, keeping the structure.

**Severity rules — classify each finding yourself from its content:**

The `/code-review` skill does NOT emit severity keywords (CRITICAL/HIGH/etc.) — it lists numbered findings with a link to the code. The `pr-review-toolkit` uses its own labels (`Critical` / `Important` / `Suggestions`). Map both onto the canonical scheme below by reading the content of each finding:

- **CRITICAL:** production/security/data-integrity bug (SQL injection, auth bypass, data leak across users/tenants, data loss or corruption, destructive migration without backfill, silent failure on a critical path). Also: any finding labeled `Critical` by `pr-review-toolkit`.
- **HIGH:** bug with high incident probability (N+1 query on a hot endpoint, race condition, unhandled error on an important path, missing tests for new logic, missing index on a heavily queried column). Also: `Important` from `pr-review-toolkit`.
- **MEDIUM:** quality problem that becomes technical debt (suggested refactor, oversized method/function, log without context, outdated comment). Also: `Suggestions` from `pr-review-toolkit`.
- **LOW:** style, optional suggestion (spacing, variable naming, nit).

**Default when in doubt:** MEDIUM (not CRITICAL — avoids severity false positives).
